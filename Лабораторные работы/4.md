# Лабораторная работа № 4. Сетевое взаимодействие агента

## Задание

Доработайте консольного агента из лабораторной работы № 3. Добавьте команду, которая через HTTPS получает данные из внешнего API и показывает пользователю результат. Проверьте работу команды автоматическими тестами с подменой сетевого взаимодействия.

### Порядок выполнения

1. После одобрения ЛР № 3 слить `task3` в `main`, обновить локальную `main` и создать от неё ветку `task4`.
2. Выбрать HTTPS API и придумать команду, для которой нужны его данные. Например, помощник по учёбе может показать погоду для указанного города, помощник по чтению — найти книгу по названию, помощник по расходам — получить курс указанной валюты.
3. Посмотреть пример запроса и ответа с помощью `curl` (в PowerShell — `curl.exe`) или другого HTTP-клиента. Определить, какие параметры отправлять и какие поля ответа нужны агенту.
4. Реализовать запрос `GET` с помощью HTTP-библиотеки своего языка. Задать таймаут, оставить включённой проверку TLS-сертификата и проверить HTTP-статус перед разбором JSON успешного ответа.
5. Добавить команду в справку. Обработать неправильный ввод, сетевые сбои, таймаут, ошибочный HTTP-статус и ответ, который невозможно разобрать или в котором отсутствуют обязательные данные.
6. Добавить автоматические тесты с подменой сетевого транспорта или HTTP-клиента. Запустить все тесты и измерить покрытие.
7. Обновить `README.md`, сделать минимум три содержательных коммита и открыть MR или PR из `task4` в `main`. Указать в описании результаты тестов и процент покрытия.
8. Предоставить преподавателю доступ, назначить его reviewer и отправить отдельное письмо со ссылкой. Тема письма — `ИТ — ЛР 4 — ФИО — группа`.

## Правила и ограничения

- Работа выполняется индивидуально в прежнем репозитории. Тема, язык, прежние команды и сохранение состояния агента сохраняются. Для Python можно использовать HTTPX и `MockTransport` из лекции.
- Сетевой вызов отделите от чтения команд и вывода в консоль, чтобы его можно было проверить автоматическим тестом.
- Автоматические тесты запускаются без реальных обращений к внешнему API. В успешном сценарии проверьте метод, адрес и параметры запроса, а также результат обработки подготовленного ответа. Отдельно проверьте таймаут, ошибочный HTTP-статус и некорректный ответ.
- Для оценки учитывается покрытие строк бизнес-логики, хранилища и кода работы с API, включая модули, которые тесты не запускали. Код консольного интерфейса, тесты и сторонние зависимости исключаются из расчёта.
- Исключите из Git локальные данные, окружение, кеши и локальные отчёты о покрытии. Если API требует ключ, передавайте его через переменную окружения и укажите её имя в README. Ключ не должен попадать в репозиторий или примеры команд.
- При оценивании коммитов учитываются содержательные изменения этой работы.
- **Сливать MR или PR до одобрения преподавателя запрещено.** Исправления отправляются новыми коммитами в `task4`.
- **Без отдельного письма со ссылкой MR или PR не рассматривается.** В GitLab преподавателю нужна роль минимум `Developer`, в GitHub — доступ как collaborator.
- Допуск к защите предоставляется после одобрения работы в MR или PR. Защита обязательна. Для сдачи нужен хотя бы один правильный ответ из трёх. Повторная защита возможна на лабораторных занятиях до конца семестра. Учитывается лучший результат.

### Срок сдачи

На выполнение отводится **две недели с момента выдачи задания**. Точную дату и время окончания срока сообщает преподаватель.

До окончания срока необходимо отправить выполненную работу, открыть содержательный MR или PR, предоставить доступ и отправить ссылку на почту преподавателя. Пустой запрос не считается сдачей.

Дата сдачи определяется по **наиболее позднему времени** из четырёх событий для запроса, по которому сдаётся работа:

- отправка последнего коммита сдаваемой работы на платформу;
- создание MR или PR;
- предоставление преподавателю доступа к репозиторию;
- отправка письма со ссылкой на этот запрос.

Учитывается время отправки коммитов на платформу, а не локальная дата их создания. **Любые доработки, включая исправления по замечаниям преподавателя, обновляют дату сдачи.** Если они отправлены после срока, доступный максимум снижается. Открытие пустого запроса в пределах срока не сохраняет первоначальную дату сдачи. Время проверки, одобрения и защиты в расчёт просрочки не входит.

За каждую начавшуюся неделю просрочки максимум снижается на **10% от исходного максимума**, но не ниже **60%**:

| Просрочка | Максимум |
| --- | --- |
| Нет | 20 баллов |
| До 7 суток включительно | 18 баллов |
| Более 7, до 14 суток включительно | 16 баллов |
| Более 14, до 21 суток включительно | 14 баллов |
| Более 21 суток | 12 баллов |

Итоговый балл — сумма баллов за итоговую версию работы и защиту, ограниченная максимумом с учётом просрочки. Например, работа отправлена вовремя, но исправления отправлены через 3 суток после срока: максимум составит 18 баллов. При результате 19 баллов итог будет 18, при результате 15 — 15.

## Критерии оценивания

Максимум — **20 баллов, из них 17 за работу и 3 за защиту** до учёта просрочки. Оценивается итоговая версия работы. За невыполненный критерий начисляется 0 баллов.

| 2 | Новая команда указана в справке, принимает предусмотренные аргументы и выполняет полезную для агента операцию с данными внешнего API | 1 |

| 4 | Обработаны ошибки пользовательского ввода. При неизвестной команде и при некорректных аргументах приложение сообщает об ошибке и продолжает работу | 1 |

## Вопросы для защиты

После одобрения работы преподаватель задаёт **три вопроса из списка**. За каждый правильный ответ с объяснением начисляется **1 балл**. Отвечайте на примере своего проекта и при необходимости показывайте код или запуск. Письменные ответы в README не требуются.

1. Кто выступает клиентом и кто сервером при выполнении новой команды?
2. Из каких частей состоит URL вашего запроса? Какую роль играют доменное имя, порт, путь и параметры?
3. Как клиент узнаёт IP-адрес сервера? Какую роль играет DNS?
4. Чем TCP отличается от UDP с точки зрения доставки данных?
5. Что добавляет TLS при работе по HTTPS? Зачем клиент проверяет сертификат сервера?
6. Покажите, как формируется ваш запрос. Как агент использует параметры пользователя?
7. Как приложение отличает таймаут от ошибочного HTTP-статуса? Что увидит пользователь в каждом случае?
8. Что произойдёт, если сервер вернёт успешный статус, но в JSON не окажется нужного поля?
9. Что подменяет ваш тест? Как он проверяет сформированный запрос и обработку ответа без подключения к серверу?
10. Что показывает покрытие строк? Какую ошибку при работе с API можно пропустить даже при высоком покрытии?
