# Работа с файлами и автоматизированное тестирование

На прошлой лекции мы с вами начали разрабатывать ИИ-агента для управления задачами. Напомню, что пока у нас пять команд, которые работают без обращения к языковой модели (LLM). Текущая версия проекта уже наводит на пару вопросов, которые лучше решить на берегу.

## Как хранятся данные

Давайте запустим наше приложение из корня репозитория:

```bash
uv run it-taskagent
```

Добавим пару задач и выйдем из приложения:

```text
> add
Enter task title: ПРЕСС КАЧАТ
> add
Enter task title: БЕГИТ
> list
0. [ ] ПРЕСС КАЧАТ
1. [ ] БЕГИТ

> exit
```

Вопрос: если мы сейчас опять запустим приложение, что выведет команда `list`? Список будет пустым.

```text
uv run it-taskagent
> list

```

С чем это связано? Пока мы храним задачи в списке `tasks`. Но где хранится сам список?

Схематично работу ЭВМ можно представить так:

- Процессор выполняет инструкции и обрабатывает данные.
- Оперативная память хранит данные работающих программ. Она энергозависима: без питания её содержимое теряется.
- Постоянное хранилище, например SSD или HDD, позволяет сохранять данные и после отключения питания.

При запуске Python-программы операционная система создаёт процесс, в котором работает интерпретатор. В CPython исходный код компилируется в байт-код, который затем выполняется интерпретатором. Во время выполнения создаются объекты в памяти процесса. Когда процесс завершается, ОС освобождает его память.

Наш список задач — один из таких объектов. Чтобы получить задачи при следующем запуске, нужно записать их в постоянное хранилище и прочитать оттуда при старте.

Данные можно хранить в текстовом файле, в двоичном формате или с помощью специализированного ПО, например системы управления базами данных. СУБД мы рассмотрим позже, а в этой лекции будем хранить задачи в текстовом файле в формате JSON.

## Что такое файловая система?

Для начала давайте создадим в пакете `it_taskagent` модуль `file_storage.py`. В нём нам понадобятся две функции:

```python
# Функция для сохранения данных в файловое хранилище
def save_storage(data: list[dict]) -> None:
    pass


# Функция для загрузки данных из файлового хранилища
def load_storage() -> list[dict]:
    pass

```

Давайте реализуем функцию `save_storage`:

```python
# Вводим константу для имени файла, в котором будут храниться данные
STORAGE_FILE = "tasks.txt"


def save_storage(data: list[dict]) -> None:
    # Используем встроенную функцию open() для открытия файла в режиме записи ("w")
    # Также явно укажем кодировку файла
    file = open(STORAGE_FILE, "w", encoding="utf-8")
    # Записываем данные в файл, преобразовав их в строку с помощью str()
    file.write(str(data))
    # Закрываем файл после записи
    file.close()
```

Давайте вызовём эту функцию из `add_task` в `tasks.py`. Остальные функции оставим на месте:

```python
from .file_storage import save_storage

tasks: list = []


def add_task(title: str) -> None:
    tasks.append({"title": title, "done": False})
    save_storage(tasks)
```

Запустим приложение из корня репозитория и добавим пару задач. Появится файл `tasks.txt` со следующим содержимым:

```text
[{'title': 'ПРЕСС КАЧАТ', 'done': False}, {'title': 'БЕГИТ', 'done': False}]
```

Давайте рассмотрим подробнее, что мы сделали.

Функция `open()` открывает файл в указанном режиме. В нашем случае это режим записи `"w"`. Схематично это выглядит так:

- Программа передаёт в `open()` путь `tasks.txt` и режим `"w"`.
- Интерпретатор обращается к ОС. Она разрешает относительный путь от текущего рабочего каталога.
- Если файла ещё нет, он создаётся. Если файл уже есть, его содержимое обрезается до нулевой длины прямо при открытии. Поэтому экспериментируйте с учебным файлом, данные из которого можно потерять.
- ОС возвращает файловый дескриптор, а Python предоставляет нам файловый объект, через который мы записываем данные.

Файловая система — это способ организации файлов, каталогов и их метаданных. Например, в Windows широко используется NTFS, в Linux распространена ext4, в системах Apple используется APFS, а на съёмных накопителях часто встречаются FAT32 и exFAT.

Наш `tasks.txt` — обычный файл, содержимое которого можно представить как последовательность байтов. В выражении `file.write(str(data))` функция `str()` строит текстовое представление списка словарей. При записи текст кодируется в байты, в нашем случае в UTF-8. Запись буферизуется: часть данных может какое-то время оставаться в памяти, прежде чем Python передаст её операционной системе.

Файловая система хранит байты, а приложение интерпретирует их как текст, изображение или аудио в зависимости от формата. Расширение помогает определить предполагаемый формат. Можно назвать файл `tasks.jpg`, но картинкой от этого он не станет.

Файл появился в корне репозитория, потому что мы запустили приложение оттуда. Если запустить программу с рабочим каталогом `src`, тот же относительный путь укажет на `src/tasks.txt`.

Каталог позволяет организовать файлы и другие каталоги в иерархию. Вот какие обозначения понадобятся нам при работе с путями:

- `/` разделяет части пути в Unix-подобных системах. Например, `/home/student/tasks.txt` — абсолютный путь от корневого каталога. В Windows обычный разделитель — `\`, а абсолютный путь может выглядеть как `C:\Users\student\tasks.txt`.
- `.` обозначает текущий каталог. В нашем примере `tasks.txt` и `./tasks.txt` указывают на один файл.
- `..` обозначает родительский каталог. Путь `../tasks.txt` укажет на файл на уровень выше рабочего каталога.

Если мы хотим хранить задачи в каталоге `data`, можем создать его и указать путь одним из двух способов:

```python
# Абсолютный путь к файлу
STORAGE_FILE = "/home/student/data/tasks.txt"

# Относительный путь к файлу
STORAGE_FILE = "./data/tasks.txt"
```

У обоих вариантов есть свои особенности. Абсолютный путь привязан к конкретному расположению каталога: у вашего друга домашний каталог может называться `vasya`, а не `student`. Относительный путь зависит от текущего рабочего каталога процесса (CWD, current working directory).

Для работы с путями я буду использовать модуль стандартной библиотеки `pathlib`. Давайте разместим файл с задачами в каталоге `data`:

```python
from pathlib import Path

# Относительный путь data/tasks.txt
STORAGE_FILE = Path("data", "tasks.txt")
# Создание директории, если она не существует
STORAGE_FILE.parent.mkdir(parents=True, exist_ok=True)


def save_storage(data: list[dict]) -> None:
    # Path предоставляет метод open(), который открывает файл в указанном режиме
    file = STORAGE_FILE.open("w", encoding="utf-8")
    file.write(str(data))
    file.close()
```

Класс `Path` собирает путь из частей по правилам текущей ОС. Метод `mkdir(parents=True, exist_ok=True)` создаёт недостающие каталоги и допускает, что каталог уже существует. При добавлении задачи в нём появится или обновится `tasks.txt`.

В этой лекции мы запускаем приложение из корня репозитория, поэтому `data` создаётся там. В приложениях расположение файлов обычно выбирают по их назначению. Например, в Unix-подобных системах для временных файлов часто используют `/tmp`.

### Зачем закрывать файлы?

Скорость вычислительной задачи обычно ограничена каким-то ресурсом. Для нашей работы полезно различать два случая.

CPU-bound задача ограничена скоростью вычислений. Пример — длительный арифметический расчёт. I/O-bound задача проводит значительную часть времени в ожидании ввода-вывода, например чтения с диска или ответа по сети. Когда мы вынесли задачи в файл, у приложения появилась операция файлового ввода-вывода.

Буферизация позволяет объединить небольшие записи, чтобы реже обращаться к ОС. Python передаёт накопленные данные при заполнении буфера, явном вызове `flush()` или закрытии файла методом `close()`. После этого данные всё ещё могут оставаться в системном кэше.

Что произойдёт, если завершить процесс сразу после `write()`? Попробуем на учебном файле: при открытии в режиме `"w"` его прежнее содержимое будет потеряно.

```python
from pathlib import Path

# Модуль os предоставляет функции для работы с операционной системой.
import os

STORAGE_FILE = Path("data", "tasks.txt")
STORAGE_FILE.parent.mkdir(parents=True, exist_ok=True)


def save_storage(data: list[dict]) -> None:
    file = STORAGE_FILE.open("w", encoding="utf-8")
    file.write(str(data))
    # Немедленно завершает процесс Python с кодом выхода 1,
    # что указывает на ошибку.
    os._exit(1)
    file.close()
```

После добавления задачи процесс завершится. Для короткой записи файл может остаться пустым: `os._exit()` завершает процесс без сброса буферов Python, и до `file.close()` выполнение не дойдёт.

Чтобы закрывать файл автоматически, в Python есть конструкция `with`. Файловый объект работает как контекстный менеджер: при выходе из блока он закрывает файл, даже если внутри блока возникло исключение.

```python
def save_storage(data: list[dict]) -> None:
    with STORAGE_FILE.open("w", encoding="utf-8") as file:
        file.write(str(data))

```

При выходе из `with` файл закрывается, а накопленные данные передаются ОС. Теперь приложение продолжает работать после добавления задачи.

Давайте закоммитим изменения с сообщением «Добавил сохранение задач на диск».

### Чтение файлов и JSON

Давайте напишем функцию загрузки. В режиме `"r"` файл открывается для чтения, а метод `read()` возвращает его содержимое в виде строки. Для пустого файла это будет пустая строка. Если файла ещё нет, `open()` выбросит `FileNotFoundError`. [Документация Python по open()](https://docs.python.org/3/library/functions.html#open).

Что мы прочитаем из `tasks.txt`? Строку вида `[{'title': 'ПРЕСС КАЧАТ', 'done': False}]`. Как превратить её обратно в список словарей? Представьте, что такой файл прислали вам по почте и попросили загрузить. Первый вопрос — в каком формате записаны данные?

Дальше мы будем обращаться к LLM через API, и там нам пригодится JSON (JavaScript Object Notation). Это текстовый формат обмена данными, основанный на синтаксисе JavaScript. Его широко используют в веб-API, а читать и записывать JSON можно из разных языков программирования. В Python для этого есть модуль `json`. [Документация модуля json](https://docs.python.org/3/library/json.html).

Давайте посмотрим, как выглядят наши задачи в JSON:

```json
[
    {
        "title": "ПРЕСС КАЧАТ",
        "done": false
    },
    {
        "title": "БЕГИТ",
        "done": false
    }
]
```

Квадратные скобки обозначают массив, фигурные — объект. Внутри объекта после имени поля в двойных кавычках идёт двоеточие, а затем значение. Например, значение поля `"title"` — строка, значение `"done"` — логическое значение `false`. JSON также поддерживает числа, например `1`.

Давайте запишем наш список в JSON, или, другими словами, сериализуем его:

```python
# Модуль для работы с JSON
import json
from pathlib import Path

# Изменили расширение файла на .json
STORAGE_FILE = Path("data", "tasks.json")
STORAGE_FILE.parent.mkdir(parents=True, exist_ok=True)


def save_storage(data: list[dict]) -> None:
    with STORAGE_FILE.open("w", encoding="utf-8") as file:
        # dump() сериализует объект Python в JSON и записывает его в файл.
        # indent=4 делает JSON более читаемым, добавляя отступы.
        json.dump(data, file, indent=4)
```

Запустите приложение и добавьте задачи заново: теперь мы записываем их в новый файл `data/tasks.json`. По умолчанию результат будет выглядеть примерно так:

```json
[
    {
        "title": "\u041f\u0420\u0415\u0421\u0421 \u041a\u0410\u0427\u0410\u0422",
        "done": false
    },
    {
        "title": "\u0411\u0415\u0413\u0418\u0422",
        "done": false
    }
]
```

По умолчанию `json.dump()` записывает символы вне ASCII с помощью escape-последовательностей. При чтении они преобразуются обратно в исходные символы. Чтобы кириллица читалась и в самом файле, добавьте аргумент `ensure_ascii=False`: `json.dump(data, file, ensure_ascii=False, indent=4)`.

```json
[
    {
        "title": "ПРЕСС КАЧАТ",
        "done": false
    },
    {
        "title": "БЕГИТ",
        "done": false
    }
]
```

Теперь десериализуем данные из файла обратно в список Python. Если файла ещё нет, начнём с пустого списка. Если файл есть, но в нём некорректный JSON, `json.load()` сообщит об ошибке.

```python
def load_storage() -> list[dict]:
    try:
        with STORAGE_FILE.open("r", encoding="utf-8") as file:
            # load() десериализует JSON из файла обратно в объект Python.
            return json.load(file)
    except FileNotFoundError:
        return []
```

И вызовем эту функцию для первоначального заполнения задач в `tasks.py`:

```python
from .file_storage import load_storage, save_storage

tasks: list[dict] = load_storage()
```

Запустим программу и убедимся в работоспособности нашего приложения:

```text
uv run it-taskagent
> list
0. [ ] ПРЕСС КАЧАТ
1. [ ] БЕГИТ

```

В каталоге `data` появилось хранилище `tasks.json`. Добавьте `data/` в `.gitignore`: пользовательские задачи и промежуточные учебные файлы не нужно включать в историю проекта.

Давайте закоммитим изменения с сообщением «Добавил JSON-хранилище».

## Проблема регрессии

Давайте вернёмся к `tasks.py`. 

```python
def add_task(title: str) -> None:
    tasks.append({"title": title, "done": False})
    save_storage(tasks)
```

Если честно, мне не очень нравится ключ `title`. Мне кажется, что сюда больше подходит `name`. Давайте заменим его в `add_task`:

```python
def add_task(name: str) -> None:
    tasks.append({"name": name, "done": False})
    save_storage(tasks)
```

А теперь запустим приложение, добавим задачу и попробуем вывести список:

```text
uv run it-taskagent
> add
Enter task title: ПРЕСС КАЧАТ
> list
...
KeyError: 'title'
```

Команда `add` по-прежнему предлагает ввести название задачи, а `list` завершается с ошибкой: `list_tasks()` обращается к ключу `title`, которого больше нет в новой записи.

В данном случае мы с вами столкнулись с регрессией кодовой базы. Регрессия (software regression) — это ситуация, когда после внесения изменений в программное обеспечение нарушается функциональность, которая ранее работала корректно.

Здесь мы нашли ошибку быстро. А если приложение состоит из множества модулей, которые взаимодействуют между собой? Проверять каждую команду вручную было бы неудобно. Давайте автоматизируем проверку. Для начала создадим каталог `tests` рядом с `src`, а в нём — файл `test_tasks.py`:

```python
# Импортируем функции и список задач
from it_taskagent.tasks import add_task, list_tasks, tasks

# Для чистоты теста очищаем список задач
tasks.clear()

# Добавляем задачу
add_task("ПРЕСС КАЧАТ")

# Проверяем, что задача была добавлена
assert len(tasks) == 1

# Проверяем, что список задач возвращает правильный формат
assert list_tasks() == "0. [ ] ПРЕСС КАЧАТ\n"

```

Инструкция `assert` проверяет условие. Если оно ложно, возникает исключение `AssertionError`. После условия через запятую можно указать сообщение об ошибке. Запустим проверку:

```bash
uv run python tests/test_tasks.py
```

При вычислении второго условия мы получим `KeyError: 'title'` ещё до сравнения строк. Теперь достаточно запустить скрипт, чтобы воспроизвести ошибку без ручного ввода команд.

Обычно для автоматизации таких проверок используют тестовый фреймворк. В стандартной библиотеке Python есть `unittest`, а в этом курсе мы будем использовать `pytest`. Такие проверки небольших частей программы называют модульными тестами (unit tests).

## Pytest

Для начала давайте добавим зависимость `pytest` в наш проект

```bash
uv add --dev pytest
```

Как и `ruff`, эта зависимость попадёт в группу `dev`. Команда обновит `pyproject.toml` и `uv.lock` и по умолчанию установит зависимость в окружение проекта.

```bash
uv run pytest
```

При сборе тестов `pytest` импортирует `test_tasks.py`. Пока проверки находятся на уровне модуля, они выполняются прямо при импорте, поэтому `KeyError` появляется как ошибка сбора.

По умолчанию `pytest` ищет, в частности, функции с именами `test_*` в файлах `test_*.py` или `*_test.py`. Давайте перенесём проверки внутрь тестовой функции:

```python
from it_taskagent.tasks import add_task, list_tasks, tasks


def test_list_task():
    tasks.clear()

    add_task("ПРЕСС КАЧАТ")
    assert len(tasks) == 1
    assert list_tasks() == "0. [ ] ПРЕСС КАЧАТ\n"

```

Запустим `uv run pytest -q`. Параметр `-q` сокращает вывод. На этот раз `pytest` соберёт тест и покажет ошибку при его выполнении:

```text
FAILED tests/test_tasks.py::test_list_task - KeyError: 'title'
```

Давайте обновим `list_tasks()`, чтобы она использовала новый ключ:

```python
def list_tasks() -> str:
    result = ""
    for i, task in enumerate(tasks):
        result += f"{i}. [{'X' if task['done'] else ' '}] {task['name']}\n"

    return result
```

Повторим `uv run pytest -q`. Теперь тест проходит. Вы могли заметить, что перед проверкой я очищаю список задач. Давайте добавим второй тест и временно уберём очистку в обоих тестах. 

```python
from it_taskagent.tasks import add_task, list_tasks, tasks


def test_add_task():
    add_task("ПРЕСС КАЧАТ")
    assert len(tasks) == 1
    assert tasks[0]["name"] == "ПРЕСС КАЧАТ"
    assert tasks[0]["done"] is False


def test_list_task():
    # Временно закомментировал очистку списка задач
    # tasks.clear()

    add_task("ПРЕСС КАЧАТ")
    assert len(tasks) == 1
    assert list_tasks() == "0. [ ] ПРЕСС КАЧАТ\n"

```

Будут ли такие тесты успешны? Если нет, то где именно они сломаются?

После запуска `uv run pytest -q` первый тест проходит, а второй получает `AssertionError: assert 2 == 1`: в списке осталась задача из предыдущего теста. Поэтому тесты важно изолировать друг от друга.

Каждый раз писать вызов очистки неудобно. В `pytest` для подготовки состояния перед тестом есть фикстуры. Добавим к двум тестам такую фикстуру:

```python
import pytest

from it_taskagent.tasks import add_task, list_tasks, mark_task_done, tasks


# Объявляем фикстуру, которая будет автоматически вызываться перед каждым тестом
@pytest.fixture(autouse=True)
def clear_tasks() -> None:
    tasks.clear()
```

Декоратор `@pytest.fixture` объявляет фикстуру. Параметр `autouse=True` означает, что она будет автоматически запускаться перед каждым тестом в этом модуле. Теперь оба теста начинают с пустого списка. [Документация pytest по фикстурам](https://docs.pytest.org/en/stable/how-to/fixtures.html).

Иногда нужно проверить одну функцию на разных входных данных. Вместо цикла можно использовать декоратор `@pytest.mark.parametrize`: `pytest` выполнит тест отдельно для каждого индекса. Фикстуру `add_tasks` запросим по имени в параметрах тестовой функции:

```python
# Вспомогательная фикстура для добавления нескольких задач
@pytest.fixture
def add_tasks() -> None:
    tasks.extend(
        [
            {"name": "ПРЕСС КАЧАТ", "done": False},
            {"name": "БЕГИТ", "done": False},
            {"name": "АТЖУМАНЯ", "done": False},
        ]
    )


# Параметризованный тест для проверки mark_task_done с разными индексами
@pytest.mark.parametrize("idx", [0, 1, 2])

def test_mark_task_done(add_tasks, idx):
    mark_task_done(idx)
    assert tasks[idx]["done"] is True

```

Чтобы проверить, что функция выбрасывает ожидаемое исключение, используем `pytest.raises()`:

```python
def test_mark_task_done_invalid_index(add_tasks):
    # Проверка пройдёт, если внутри блока возникнет IndexError
    with pytest.raises(IndexError):
        mark_task_done(3)

```

Теперь посмотрим на слона в комнате. Что произойдёт, если отключить фикстуру `clear_tasks` и дважды запустить один и тот же тест?

```bash
uv run pytest -q -k test_add_task
```

Параметр `-k` отбирает тесты по выражению, которое сопоставляется с их именами. Первый запуск пройдёт, а во втором проверка длины списка получит две задачи вместо одной.

При импорте `tasks.py` список заполняется из файла, а `add_task()` записывает его обратно. Даже два отдельных запуска тестов оказываются связаны одним файлом. Это уже вопрос архитектуры: модуль работы с задачами сам управляет хранилищем. Давайте вынесем эту ответственность в точку входа, а в `file_storage.py` добавим возможность задать путь к файлу:

```python
import json
from pathlib import Path

# Определим приватную переменную для хранения пути к файлу
_storage_path = Path("data", "tasks.json")


def init_storage(path: Path) -> None:
    """Инициализация хранилища задач."""
    # Используем global для изменения глобальной переменной _storage_path
    global _storage_path
    _storage_path = path
    _storage_path.parent.mkdir(parents=True, exist_ok=True)


def save_storage(data: list[dict]) -> None:
    """Сохранение данных в хранилище задач."""
    with _storage_path.open("w", encoding="utf-8") as file:
        json.dump(data, file, ensure_ascii=False, indent=4)


def load_storage() -> list[dict]:
    """Загрузка данных из хранилища задач."""
    try:
        with _storage_path.open("r", encoding="utf-8") as file:
            data = json.load(file)
            return data
    except FileNotFoundError:
        return []

```

Имя `_storage_path` начинается с подчёркивания: по соглашению это внутренняя переменная модуля. Внешний код задаёт путь через `init_storage()`. Инструкция `global` позволяет этой функции присвоить значение переменной на уровне модуля. Строки в тройных кавычках в начале функций — строки документации, или docstrings.

Теперь перепишем модуль `tasks.py`:

```python
_tasks: list[dict] = []


def init_tasks(tasks: list[dict]) -> None:
    """Инициализация списка задач."""
    global _tasks
    _tasks = tasks


def get_tasks() -> list[dict]:
    """Получение списка задач."""
    return _tasks


def add_task(name: str) -> None:
    """Добавление новой задачи."""
    _tasks.append({"name": name, "done": False})


def list_tasks() -> str:
    """Вывод списка задач в виде строки."""
    result = ""
    for i, task in enumerate(_tasks):
        result += f"{i}. [{'X' if task['done'] else ' '}] {task['name']}\n"

    return result


def mark_task_done(index: int) -> None:
    """Пометка задачи как выполненной."""
    if index < 0:
        raise IndexError("Task index must be non-negative")
    _tasks[index]["done"] = True

```

Модуль `tasks` теперь работает со списком в памяти. Получить список можно через `get_tasks()`.

Давайте перепишем модуль точки входа `task_agent.py`. В `cli.py` можно также переименовать локальную переменную `title` в `name` и передавать её в `add_task(name)`.

```python
from pathlib import Path

from .cli import cli
from .file_storage import init_storage, load_storage, save_storage
from .tasks import get_tasks, init_tasks


def main() -> None:
    # Инициализация хранилища задач и загрузка существующих задач
    init_storage(Path("data", "tasks.json"))
    # Загрузка задач из хранилища
    loaded_tasks = load_storage()

    # Инициализация списка задач в модуле tasks
    init_tasks(loaded_tasks)

    cli()

    # Сохранение задач в хранилище при завершении работы приложения
    save_storage(get_tasks())

```

Теперь `main()` задаёт путь к хранилищу, загружает задачи и передаёт их в `init_tasks()`. Это простая форма внедрения зависимостей (dependency injection): модуль получает нужные данные снаружи. После обычного выхода из `cli()` список сохраняется. При аварийном завершении последние правки могут потеряться.

Заменим содержимое `tests/test_tasks.py`. Теперь будем получать список задач через `get_tasks()`, а фикстура очистки снова будет запускаться перед каждым тестом.

## TDD

Наш рассказ о тестировании был бы неполным без TDD (Test-Driven Development), или разработки через тестирование. Сначала пишем тест на новое поведение и убеждаемся, что он падает. Затем добавляем минимальную реализацию, запускаем тесты и при необходимости улучшаем код, сохраняя его поведение.

Давайте реализуем удаление задачи по индексу. Добавим в `tests/test_tasks.py` импорт `from it_taskagent.tasks import delete_task` и новый тест:

```python

def test_delete_task(add_tasks):
    # Удаляем вторую задачу (индекс 1)
    delete_task(1)
    current_tasks = get_tasks()
    assert len(current_tasks) == 2
    assert current_tasks[0]["name"] == "ПРЕСС КАЧАТ"
    assert current_tasks[1]["name"] == "АТЖУМАНЯ"

```

Запустим `uv run pytest -q -k delete_task`. Пока функции нет, `pytest` остановится при сборе тестов с ошибкой `ImportError: cannot import name 'delete_task'`. Добавим в `tasks.py` минимальную реализацию:

```python
def delete_task(idx: int) -> None:
    """Удаление задачи по индексу."""
    if idx < 0:
        raise IndexError("Task index must be non-negative")
    _tasks.pop(idx)

```

Повторим `uv run pytest -q -k delete_task`. Теперь тест проходит. При попытке удалить задачу по отсутствующему индексу функция пока выбрасывает `IndexError`. Я хочу изменить поведение: пусть функция возвращает удалённую задачу, а для недопустимого индекса — `None`. Сначала обновим тесты:

```python
def test_delete_task(add_tasks):
    # Теперь мы ожидаем, что функция delete_task возвращает удалённую задачу
    task = delete_task(1)
    current_tasks = get_tasks()
    assert len(current_tasks) == 2
    assert current_tasks[0]["name"] == "ПРЕСС КАЧАТ"
    assert current_tasks[1]["name"] == "АТЖУМАНЯ"
    # Проверяем, что возвращённая задача соответствует удалённой
    assert task == {"name": "БЕГИТ", "done": False}


@pytest.mark.parametrize("idx", [-1, 10])
def test_delete_task_invalid_index(add_tasks, idx):
    assert delete_task(idx) is None
    assert len(get_tasks()) == 3
```

Снова запустим `uv run pytest -q -k delete_task`. Первый тест получит `None` вместо словаря, а проверки недопустимых индексов завершатся с `IndexError`. Добавим нужное поведение:

```python
def delete_task(idx: int) -> dict | None:
    """Удаление задачи по индексу."""
    if idx < 0:
        return None
    try:
        return _tasks.pop(idx)
    except IndexError:
        return None

```

Теперь выполним `uv run pytest -q`, чтобы проверить весь набор тестов. Функция удаления пока доступна только из кода. Давайте закоммитим изменения с сообщением «Добавил удаление задачи».

## Покрытие кода тестами

Когда мы пишем тест перед реализацией, мы заранее описываем ожидаемое поведение функции. А чтобы увидеть, какие части программы выполняются при запуске тестов, измерим покрытие.

Давайте посмотрим наше текущее покрытие. Для начала установим плагин. [Документация pytest-cov](https://pytest-cov.readthedocs.io/en/latest/).

```bash
uv add --dev pytest-cov
```

Запустим тесты с измерением покрытия пакета `it_taskagent`:

```bash
uv run pytest -q --cov=it_taskagent
```

В отчёте для каждого модуля будут указаны:

- `Stmts` — число исполняемых операторов, учитываемых при измерении покрытия.
- `Miss` — сколько из них ни разу не выполнилось при запуске тестов.
- `Cover` — доля выполненных операторов в процентах. Строка `TOTAL` показывает покрытие по всем модулям вместе.

Например, если в модуле учтено 20 операторов и 4 из них ни разу не выполнились, покрытие составит 80%. В нашем проекте тесты вызывают функции задач и хранилища, поэтому отчёт покажет выполненный код в этих модулях. Команды интерфейса мы в тестах пока не запускаем.

Покрытие показывает, какой код выполнился. Давайте посмотрим, что измерение покажет для такого теста:

```python
def test_wrong_add():
    add_task("ПРЕСС КАЧАТ")
```

Вызов выполнит тело `add_task()`. Проверил ли тест, что в списке появилась нужная задача? Для этого нужны проверки результата, как в нашем `test_add_task()`.

Давайте закоммитим изменения с сообщением «Подключил pytest-cov».
