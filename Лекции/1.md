## Введение в курс

Этот курс посвящён разработке приложений. За два семестра мы познакомимся с совместной разработкой, основами работы с сетью, фреймворками, тестированием и развёртыванием. Все эти темы я буду показывать на примере разработки собственного ИИ-агента.

Наша цель — вместе разработать ИИ-агента для управления задачами. В этом проекте агент будет обращаться к большой языковой модели (LLM, large language model) и использовать инструменты для работы с внешними сервисами. Например, инструмент может создавать задачу или получать список задач.

```text
Пользователь
     ↓
    Агент ←────→ LLM
     ↓
 Инструменты
     ↓
Внешние сервисы
```

Лекции будут похожи на мастер-классы: я объясняю тему и сразу показываю, как всё работает. Практики будет больше, чем теории. На лабораторных работах вам нужно будет самостоятельно повторить и применить показанное на лекции. В конце курса вы должны будете разработать собственного ИИ-агента.

По плану в этом семестре у нас остаётся шесть лекций и шесть лабораторных работ. Каждое занятие продолжает предыдущее: нельзя выполнить шестую лабораторную работу, пропустив первую.

Лекции и задания я буду выкладывать в GitLab и дублировать на GitHub — это платформы для хранения проектов и совместной разработки. Вы можете пользоваться любой из них. Работы будете выполнять в своём личном репозитории, то есть проекте с историей изменений, и создавать запрос на слияние: merge request (MR) в GitLab или pull request (PR) в GitHub. Через него вы предложите включить выполненную работу в основную ветку проекта. Подробнее эти понятия разберём дальше.

Сначала я проверяю работу, затем вы защищаете её очно. На занятие нужно приходить с готовой работой; там же можно получить консультацию. Можно представить, что у нас один большой проект, разделённый на двухнедельные этапы — спринты.

За работы я буду ставить баллы, а в конце семестра — оценку по их сумме. На каждую работу отводится две недели. За каждую неделю просрочки максимально доступный балл снижается на 10% от исходного максимума, но не ниже 60% от него. Например, если максимум за работу — 100 баллов, после одной недели просрочки он составит 90, после двух — 80, после четырёх и более — 60. Главное — в течение двух недель отправить осмысленный MR или PR. Ошибки в своевременно отправленной работе влияют на фактически полученный балл, но сами по себе не снижают максимум за соблюдение срока.

Критерии оценивания и вопросы для защиты будут опубликованы вместе с заданием. Для решения лабораторных работ можно использовать любые инструменты, но вы должны понимать свой код и уметь его изменять. Это мы проверим на защите.

Примеры в курсе будут на Python: это широко используемый язык, удобный для нашего проекта. Лабораторные работы можно выполнять на любом удобном вам языке.

Сегодня поговорим о Git — системе контроля версий, которая помогает сохранять историю проекта и работать над ним вместе. Git появился в 2005 году, поэтому на момент этой лекции ему уже больше двадцати лет. [История Git](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git).

## Системы контроля версий

Представим, что вы разрабатываете приложение, например агента, и у вас есть файл `agent.py`. На следующий день вы дописали код, что-то удалили и вдруг поняли, что приложение перестало работать. Как вернуть удалённый код?

Можно заранее создать копию и вносить изменения уже в неё:

```text
agent.py
agent_final.py
```

Теперь можно вернуться к старому файлу. Но как понять, что именно изменилось? Придётся открыть два файла рядом и сравнивать их глазами или пользоваться специальным инструментом сравнения.

А если вы предложили другу Пете помочь? Каждый может редактировать свою копию:

```text
agent.py
agent_final.py
agent_final_petya.py
agent_final_vasya.py
```

Но потом изменения нужно объединить. Как понять, кто и зачем их сделал? Можно продолжать придумывать имена:

```text
agent_fix_petya.py
agent_new_feature_vasya.py
agent_final_really.py
```

Так можно и исправлять ошибки, и пробовать новую функцию, не затрагивая старую копию. На небольшом проекте этот подход иногда выручает, но по мере роста проекта становится трудно разобраться, какая версия актуальна и какие изменения нужно сохранить.

Для этих задач существуют **системы контроля версий** (СКВ; VCS, version control system). Они позволяют сохранять версии файлов, просматривать историю изменений, сравнивать версии и объединять работу нескольких разработчиков.

СКВ бывают централизованными и распределёнными. В централизованной системе основная история проекта хранится в центральном хранилище. Разработчик получает рабочую копию и отправляет изменения обратно. Без доступа к хранилищу можно продолжать редактировать локальные файлы, но операции с общей историей и публикация изменений будут недоступны. [Типы систем контроля версий](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control).

В распределённой СКВ, например Git, у разработчика обычно есть локальный репозиторий с историей проекта. Поэтому создавать коммиты, сравнивать версии и работать с ветками можно без соединения с сервером. Сервер часто используют как общее место обмена изменениями.

Если сервер потерян, историю, имеющуюся в полной локальной копии, можно восстановить из этой копии. Но неотправленные изменения других разработчиков и данные самой платформы — например, обсуждения задач — автоматически из неё не восстановятся. Кроме того, бывают сокращённые копии репозитория с неполной историей.

При совместной работе изменения нужно объединять. Git часто делает это автоматически, даже если два человека редактировали один файл. Если изменения нельзя однозначно совместить, возникает конфликт, который нужно разрешить вручную. Ниже мы попробуем это на практике.

## Что такое Git?

Git — распределённая система контроля версий, которую первоначально разработал Линус Торвальдс для работы над ядром Linux. Мы будем пользоваться Git через командную строку; для него также существуют графические интерфейсы.

Главное понятие — **репозиторий**. Представим папку проекта:

```text
project/
├── main.py
├── agent.py
└── README.md
```

Пока это обычная папка с файлами. При обычной инициализации Git создаёт в ней служебный каталог `.git`:

```text
project/
├── main.py
├── agent.py
├── README.md
└── .git/
```

В `.git` хранится история проекта, ссылки на ветки, локальные настройки и другая служебная информация. Файлы, которые вы открываете и редактируете вне `.git`, образуют **рабочее дерево**. В более сложных конфигурациях Git служебные данные могут находиться в другом месте; для наших примеров достаточно обычного варианта. [Инициализация репозитория](https://git-scm.com/docs/git-init).

Точки сохранения истории называются **коммитами**. Коммит содержит ссылку на снимок отслеживаемых файлов, сведения об авторе и о том, кто создал коммит, даты и сообщение. Он также ссылается на родительские коммиты: у первого коммита родителей нет, у обычного — один, а у коммита слияния обычно два. Поэтому история может быть не только цепочкой, но и графом с ответвлениями и слияниями.

Снимок не означает, что Git при каждом коммите создаёт отдельную полную копию каждого файла. Содержимое хранится в объектах Git. Объект с содержимым файла называют **blob**, а имена файлов и структуру каталогов описывают объекты дерева. Если содержимое файла не изменилось, новый снимок может использовать тот же blob:

```text
Снимок коммита A          Снимок коммита B
main.py   → blob X        main.py   → blob Z  ← содержимое изменилось
README.md → blob Y        README.md → blob Y  ← содержимое прежнее

Коммит B ссылается на коммит A как на родителя.
```

Это упрощённая схема: коммит ссылается на дерево, а уже дерево — на содержимое файлов. Буквы обозначают условные объекты. [Объекты Git](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects).

Git позволяет вести разные линии разработки с помощью **веток**. Ветка — это именованная ссылка на коммит. Когда вы создаёте новый коммит в текущей ветке, её ссылка перемещается на него. Так можно разрабатывать новую функцию отдельно от основной версии проекта.

Git, GitHub и GitLab — разные вещи. Git управляет версиями, а GitHub и GitLab предоставляют платформы вокруг него: хранят удалённые репозитории, помогают обсуждать изменения и автоматизировать проверки и развёртывание. Такие автоматические процессы часто называют CI/CD: continuous integration — непрерывная интеграция, continuous delivery/deployment — непрерывная доставка или развёртывание.

## Установка и первоначальная настройка

В Windows установите Git по инструкции на [официальном сайте](https://git-scm.com/install/). В Linux и macOS Git часто уже доступен на компьютере. В Linux он может входить в набор предустановленных пакетов дистрибутива, а в macOS поставляется вместе с инструментами разработчика Xcode Command Line Tools. Наличие Git зависит от комплектации системы: сначала проверьте его командой `git --version`, показанной ниже. Если в macOS инструменты разработчика ещё не установлены, при запуске команды система может предложить их установить. В Linux при необходимости установите Git через менеджер пакетов своего дистрибутива. [Установка Git](https://git-scm.com/book/en/v2/Getting-Started-Installing-Git).

В Windows после установки можно работать из PowerShell или Git Bash, который входит в Git for Windows. Для этой лекции я рекомендую Git Bash: в нём доступны команды `touch`, `ls` и `cat`, используемые в примерах. В Linux и macOS подойдёт обычный терминал с соответствующими командами.

Откройте терминал и выполните:

```bash
git --version
```

Например, результат может выглядеть так:

```text
git version 2.53.0.windows.1
```

У вас номер версии может отличаться. Для выполнения всех примеров нужен Git 2.28 или новее.

Команды и примерный вывод терминала ниже показаны раздельно. Команды можно копировать без символа приглашения `$`. Хеши коммитов, даты, пути и подробности вывода у вас будут другими.

В коммитах сохраняются имя и электронная почта автора. Для учебного проекта я рекомендую указать полное ФИО и студенческую почту. Подставьте свои данные:

```bash
git config --global user.name "Ivan Ivanov"
git config --global user.email "ivan@example.com"
```

Здесь `git` — программа, `config` — команда настройки, `user.name` и `user.email` — имена параметров. Опция `--global` задаёт настройки для текущего пользователя во всех его репозиториях, если они не переопределены более конкретными настройками.

Для отдельного репозитория можно использовать `--local`, выполняя команду внутри него. Например:

```bash
git config --local user.name "Ivan Ivanov"
```

Посмотреть действующие настройки можно так:

```bash
git config --list
```

Учтите, что эти данные входят в историю коммитов и будут видны читателям публичного репозитория. [Настройки Git](https://git-scm.com/docs/git-config).

## Создаём проект курса

Создадим каталог будущего проекта и перейдём в него:

```bash
mkdir ai-agent
cd ai-agent
```

Команда `mkdir` создаёт каталог, `cd` делает его текущим каталогом терминала. Теперь создадим пустой файл:

```bash
touch README.md
ls
```

Если файла нет, `touch` создаёт его. Если он уже существует, команда обновляет временные метки, не очищая содержимое. Команда `ls` показывает содержимое текущего каталога.

`README.md` — текстовый файл с описанием проекта, обычно написанный на Markdown. Это язык разметки, в котором заголовки, выделение и списки задаются простыми символами. Позже посмотрим, как GitLab отображает такой файл.

Инициализируем репозиторий и сразу зададим имя основной ветки `main`:

```bash
git init -b main
```

Git сообщит об успешной инициализации и покажет путь к `.git`. Без `-b main` имя начальной ветки зависит от настроек и версии Git: вы можете встретить `main`, `master` или другое имя. Само имя не меняет принцип работы ветки.

Посмотреть в том числе имена, начинающиеся с точки, можно так:

```bash
ls -a
```

Вы увидите `README.md` и `.git`. Репозиторий пока не содержит коммитов. Давайте сделаем первый.

## Первый коммит

Перед командами нужно разобраться с тремя местами, между которыми мы будем сравнивать состояние проекта:

- **Рабочее дерево** — файлы, которые вы редактируете.
- **Индекс (staging area)** — подготовленное содержимое следующего коммита.
- **Последний коммит** — уже сохранённый снимок в истории.

Обычно работа выглядит так: изменили файл, добавили нужное содержимое в индекс, создали коммит. Индекс позволяет выбрать, какие изменения войдут в очередную точку сохранения.

Посмотрим состояние проекта:

```bash
git status
```

Пример вывода:

```text
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md

nothing added to commit but untracked files present (use "git add" to track)
```

Мы находимся в ветке `main`, коммитов ещё нет. `README.md` имеет состояние **untracked**, то есть это неотслеживаемый файл: Git видит его в рабочем дереве, но он ещё не включён в индекс или историю.

Подготовим файл к коммиту:

```bash
git add README.md
git status
```

Теперь среди строк вывода будет:

```text
Changes to be committed:
        new file:   README.md
```

Файл добавлен в индекс, а его содержимое подготовлено к коммиту — **staged**. Важно: `git add` сохраняет в индексе содержимое на момент выполнения команды. Если после этого снова отредактировать файл, новые правки нужно добавить отдельно. [Работа с индексом](https://git-scm.com/docs/git-add).

Создадим коммит. Опция `-m` задаёт сообщение:

```bash
git commit -m "Add project README"
git status
```

Пример вывода:

```text
[main (root-commit) 51ad647] Add project README
 1 file changed, 0 insertions(+), 0 deletions(-)
 create mode 100644 README.md

On branch main
nothing to commit, working tree clean
```

Первый коммит создан. Файл пустой, поэтому добавленных строк нет. `working tree clean` означает, что Git не видит изменений для фиксации и не показывает неотслеживаемых файлов.

Теперь откройте `README.md` любым текстовым редактором, запишите строку `Hello world` и сохраните файл:

```text
Hello world
```

Выполните:

```bash
git status
```

Вы увидите:

```text
Changes not staged for commit:
        modified:   README.md
```

Файл изменён, но новые данные ещё не подготовлены к коммиту. В этом примере индекс совпадает с последним коммитом, поэтому правки видны и относительно него.

Можно снова выполнить `git add README.md`, а затем `git commit`. Для уже отслеживаемых файлов есть сокращённый вариант:

```bash
git commit -a -m "Add Hello world"
```

Опция `-a` автоматически подготавливает изменения и удаления **уже отслеживаемых файлов** во всём репозитории. Новые неотслеживаемые файлы она не добавляет. Будьте внимательны: вместе с нужной правкой так можно зафиксировать другие изменения отслеживаемых файлов. [Создание коммита](https://git-scm.com/docs/git-commit).

В Windows вы можете встретить предупреждение:

```text
warning: in the working copy of 'README.md', LF will be replaced by CRLF the next time Git touches it
```

LF и CRLF — разные способы обозначить конец строки в текстовом файле. Предупреждение связано с настройками преобразования окончаний строк в Git; оно само по себе не означает, что коммит не выполнен. В последующих примерах будем опускать такие сообщения. [Окончания строк в Git](https://git-scm.com/docs/gitattributes).

Посмотрим историю:

```bash
git log
```

Git покажет коммиты, начиная с более новых: идентификатор, автора, дату и сообщение. Например, в заголовке последнего коммита можно увидеть `(HEAD -> main)`.

**HEAD** обычно указывает на текущую ветку, а она — на её последний коммит. В данном случае мы работаем в `main`. [Обозначения коммитов и HEAD](https://git-scm.com/docs/gitrevisions).

Жизненный цикл удобно представить так:

```text
Создали файл → untracked
     ↓ git add
Файл отслеживается, содержимое подготовлено в индексе
     ↓ git commit
Содержимое сохранено в истории, новых изменений нет
     ↓ отредактировали файл
Изменения в рабочем дереве, ещё не подготовлены
     ↓ git add
Изменения подготовлены в индексе
     ↓ git commit
Новый снимок сохранён в истории
```

Если `git log` открыл просмотрщик и терминал ждёт ввода, нажмите `q`, чтобы выйти.

## Изменения и история

Добавим в `README.md` вторую строку. Теперь содержимое такое:

```text
Hello world
Hello, Git
```

Сохраните файл и выполните:

```bash
git status
git diff
```

`git status` сообщит, что `README.md` изменён. `git diff` покажет сами правки. Содержательная часть вывода:

```diff
--- a/README.md
+++ b/README.md
@@ -1 +1,2 @@
 Hello world
+Hello, Git
```

Строка с `+` добавлена, строка с `-` обозначает удаление, а строка с пробелом в начале даётся для контекста. Git позволяет увидеть конкретные различия, а не только узнать, что файл изменился.

Без аргументов **`git diff` сравнивает рабочее дерево с индексом**. Сейчас индекс содержит прежнюю версию, поэтому видна новая строка. Добавим файл в индекс и сравним ещё раз:

```bash
git add README.md
git diff
git diff --staged
```

Если после `git add` вы больше не редактировали файлы, первый `git diff` ничего не выведет: рабочее дерево и индекс совпадают. **`git diff --staged` сравнивает индекс с последним коммитом** и покажет подготовленную строку `Hello, Git`. Чтобы сравнить рабочее дерево с последним коммитом, можно использовать `git diff HEAD`. [Сравнение версий](https://git-scm.com/docs/git-diff).

Зафиксируем изменение и посмотрим сокращённую историю:

```bash
git commit -m "Add Hello Git"
git log --oneline
```

Пример вывода:

```text
743af48 (HEAD -> main) Add Hello Git
1f1a0ca Add Hello world
51ad647 Add project README
```

Опция `--oneline` выводит каждый коммит одной строкой. В начале указан сокращённый хеш — идентификатор коммита. Сокращение можно использовать в командах, если оно однозначно определяет коммит в этом репозитории.

Чтобы сравнить два сохранённых снимка, передайте их идентификаторы. Следующий пример использует хеши из показанной истории; **замените их хешами из своего `git log`**:

```bash
git diff 51ad647 743af48
```

Так мы сравним пустой `README.md` из первого коммита с версией, содержащей обе строки.

Есть и относительные обозначения. `HEAD~1` — первый родитель текущего коммита, `HEAD~2` — его родитель по той же линии и так далее. В нашей линейной истории это означает «один коммит назад», «два коммита назад».

Сравним последние два снимка:

```bash
git diff HEAD~1 HEAD
```

Хорошая привычка — делать один коммит на одно логическое изменение и писать понятное сообщение. Так будет проще понять, что изменилось и зачем.

## `.gitignore`

Рано или поздно в проекте появятся файлы, которые не нужно сохранять в истории. Например, при импорте модулей в CPython — наиболее распространённой реализации Python — обычно создаётся кеш скомпилированного байткода в файлах `.pyc` внутри `__pycache__`. Этот кеш ускоряет загрузку модулей, потому что позволяет не компилировать их исходный код заново. Обычно кеш можно создать повторно, поэтому его не включают в репозиторий. [Кеш байткода Python](https://docs.python.org/3/tutorial/modules.html#compiled-python-files).

Также в проекте может быть `.env` с настройками окружения, в том числе токенами и паролями. Сам по себе этот файл — обычный текстовый файл, а не защищённое хранилище. Реальные секреты не должны попадать в репозиторий.

Для упражнения создайте в редакторе файл `.env` с **вымышленным** значением `API_TOKEN=example` и каталог `__pycache__` с любым учебным файлом внутри. Не используйте настоящий пароль или токен. `git status` покажет их как неотслеживаемые:

```text
Untracked files:
        .env
        __pycache__/
```

Если добавить такие файлы и создать коммит, их содержимое попадёт в историю. Удаление в следующем коммите не удаляет прежние версии. Если реальный секрет уже попал в историю, его нужно отозвать или заменить: одного удаления файла недостаточно.

Чтобы не добавлять ненужные файлы случайно, создадим в корне проекта `.gitignore`:

```gitignore
.env
__pycache__/
```

Это обычный текстовый файл с шаблонами игнорирования. Такие правила применяются к ещё не отслеживаемым файлам. Они **не прекращают отслеживание уже добавленного файла** и не удаляют его из прежних коммитов.

В нашем корневом `.gitignore` правило `.env` действует на файлы с таким именем на любом уровне проекта, а `__pycache__/` — на каталоги с таким именем и их содержимое. Чтобы игнорировать только `.env` в корне, используют:

```gitignore
/.env
```

Чтобы игнорировать файлы с расширением `.pyc`:

```gitignore
*.pyc
```

Восклицательный знак задаёт исключение из предыдущего правила. Например:

```gitignore
*.log
!important.log
```

Здесь файлы с именами, оканчивающимися на `.log`, игнорируются, кроме файлов с именем `important.log`. Эти шаблоны также могут совпадать с именами каталогов. Исключение не сработает, если родительский каталог целиком исключён: сначала нужно разрешить обход этого каталога. Для нашего проекта достаточно первых двух правил. [Правила `.gitignore`](https://git-scm.com/docs/gitignore).

Сохраните `.gitignore` и выполните `git status`. Теперь из новых файлов будет показан только он. Зафиксируем правила:

```bash
git add .
git diff --staged
git commit -m "Add .gitignore"
```

В `git add .` точка обозначает текущий каталог. В современных версиях Git команда подготавливает новые файлы, изменения и удаления в нём и вложенных каталогах, с учётом правил игнорирования. Поэтому перед коммитом полезно проверить подготовленные изменения.

## Ветки

Представим, что текущая ветка содержит готовое приложение, которым уже пользуются люди. Начальник говорит: «Вася, попробуй добавить в README информацию о погоде, но пока не включай её в основную версию». Нам нужно провести эксперимент и сохранить исходное состояние основной ветки.

Для этого создадим ветку `feature` и переключимся на неё:

```bash
git switch -c feature
git log --oneline
```

Команда `switch` переключает ветку, а `-c` создаёт её перед переключением. По умолчанию новая ветка начинается с текущего коммита. В истории вы увидите примерно такую строку:

```text
0bcad1e (HEAD -> feature, main) Add .gitignore
```

Обе ветки пока ссылаются на один коммит. Посмотреть локальные ветки и переключиться между ними можно так:

```bash
git branch
git switch main
git switch feature
```

В выводе `git branch` текущая ветка отмечена `*`. При переключении Git обновляет индекс и рабочее дерево под выбранную ветку. Незакоммиченные изменения иногда могут перейти с вами в другую ветку; если переключение перезаписало бы их, Git обычно откажется его выполнять. Для наших упражнений перед переключением фиксируйте нужные изменения и проверяйте `git status`. [Переключение веток](https://git-scm.com/docs/git-switch).

В ветке `feature` добавьте в `README.md` пустую строку и погоду:

```text
Hello world
Hello, Git

Sunny, +15
```

Сохраните файл и создайте коммит:

```bash
git commit -a -m "Add weather"
git log --oneline
```

Теперь указатель `feature` переместился на новый коммит, а `main` остался на прежнем:

```text
43f63d9 (HEAD -> feature) Add weather
0bcad1e (main) Add .gitignore
```

Переключимся на основную ветку и посмотрим файл:

```bash
git switch main
cat README.md
```

В нём снова только две строки:

```text
Hello world
Hello, Git
```

Предположим, эксперимент удался и изменения нужно включить в основную ветку. Находясь в `main`, выполним **слияние**:

```bash
git merge feature
git log --oneline
```

При стандартных настройках слияния в нашем примере Git сообщит `Fast-forward`. Это возможно, потому что `main` не получила собственных новых коммитов и её текущий коммит — предок коммита `feature`. Git просто передвинет `main` вперёд; отдельный коммит слияния при таком варианте не создаётся. Теперь обе ветки указывают на коммит `Add weather`, а в `README.md` основной ветки есть погода. [Слияние веток](https://git-scm.com/docs/git-merge).

Слияние меняет историю и файлы текущей ветки, но само по себе не публикует приложение и не развёртывает его на сервере.

## Конфликты

Представим, что вы работаете с Петей. Вы меняете температуру, а Петя добавляет дату к той же строке. Обе задачи начинаются от одной версии `main`, где записано `Sunny, +15`.

Для упражнения выполним работу обоих разработчиков в одном репозитории. Сначала создадим вашу ветку:

```bash
git switch main
git switch -c new_weather
```

Замените в `README.md` строку `Sunny, +15` на `Sunny, +20`, сохраните файл и выполните:

```bash
git commit -a -m "Update weather"
```

Теперь **вернитесь в `main`**, прежде чем создавать ветку Пети. Так обе ветки начнутся от одного коммита, а не одна от другой:

```bash
git switch main
git switch -c date_in_weather
```

В этой ветке погода снова `Sunny, +15`. Замените строку на `01.01.2026: Sunny, +15` и сохраните файл. Дата — условное значение для примера.

```bash
git diff
git commit -a -m "Add weather date"
```

Содержательная часть различий:

```diff
-Sunny, +15
+01.01.2026: Sunny, +15
```

Теперь объединим изменения в основной ветке:

```bash
git switch main
git merge new_weather
```

При стандартных настройках первое слияние выполнится как `Fast-forward`. Затем:

```bash
git merge date_in_weather
```

Git сообщит:

```text
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

Мы с Петей изменили одну строку по-разному. Git не может определить нужный результат и оставляет решение нам. Откройте `README.md`. При стандартном формате отображения конфликта вы увидите:

```text
Hello world
Hello, Git

<<<<<<< HEAD
Sunny, +20
=======
01.01.2026: Sunny, +15
>>>>>>> date_in_weather
```

`<<<<<<< HEAD` открывает конфликтующий участок. До `=======` находится вариант текущей ветки `main`, а после разделителя — вариант из присоединяемой ветки `date_in_weather`. Маркер `>>>>>>> date_in_weather` завершает участок.

Можно оставить один вариант или объединить их. В нашем случае нужны и новая температура, и дата. Удалите маркеры и лишние строки, чтобы получилось:

```text
Hello world
Hello, Git

01.01.2026: Sunny, +20
```

Сохраните файл, отметьте конфликт как разрешённый добавлением результата в индекс и завершите слияние:

```bash
git add README.md
git diff --staged
git status
git commit -m "Resolve weather conflict"
git log --oneline --graph
```

Перед коммитом проверьте, что в файле не осталось маркеров, а `git status` больше не показывает неразрешённых конфликтов. В отличие от первого слияния, здесь появится коммит с двумя родителями: он связывает обе линии разработки. Опция `--graph` помогает увидеть это в истории.

Если во время незавершённого слияния вы решили отказаться от него, выполните:

```bash
git merge --abort
```

Команда пытается вернуть состояние до начала слияния; сделанные при разрешении конфликта правки могут быть потеряны. `--abort` не отменяет уже завершённое слияние.

## Как отменять коммиты

Разговор о Git будет неполным, если мы не затронем механизмы для «отката» коммитов. Представим ситуацию: у вас было нормальное рабочее приложение, один из разработчиков сделал некоторое изменение в нём, закоммитил, после чего приложение сломалось. Вам необходимо быстро восстановить работоспособность приложения, то есть отменить изменения, которые привели к поломке. Это можно сделать несколькими способами.

### `revert` или как откатить коммиты с сохранением истории

Самым «мягким» способом отката является команда `revert`: она создаёт новый коммит с изменениями, обратными изменениям выбранного коммита. Например, давайте создадим ветку `revert_example` от `main`:

```bash
git switch main
git switch -c revert_example
```

Для наглядности добавьте в конец `README.md` строку `App status: working`, сохраните файл и закоммитьте изменение. Это будет коммит с работающей версией:

```bash
git commit -a -m "stable version"
```

После этого замените добавленную строку на `App status: broken`, сохраните файл и закоммитьте изменение. Так мы изобразим сломанную версию:

```bash
git commit -a -m "broken version"
git log --oneline -3
```

В истории будет что-то подобное:

```text
00b4269 (HEAD -> revert_example) broken version
6517733 stable version
dce265e (main) Resolve weather conflict
```

Хеши здесь и далее условные: у вас они будут другими. Более ранние коммиты в примерах вывода опущены. Чтобы откатить изменение через `revert`, напишем такую команду:

```bash
git revert --no-edit HEAD
git log --oneline -4
```

`HEAD` обозначает последний коммит нашей ветки, здесь мы указываем на последний коммит, **изменения которого нужно отменить**. Параметр `--no-edit` позволяет использовать автоматически подготовленное сообщение, не открывая редактор. Теперь история у нас следующая:

```text
3c7cfbe (HEAD -> revert_example) Revert "broken version"
00b4269 broken version
6517733 stable version
dce265e (main) Resolve weather conflict
```

В `README.md` снова записано `App status: working`. В этом примере мы отменили последний коммит, поэтому содержимое проекта вернулось к работающей версии. При отмене более раннего коммита `revert` убирает именно его изменения, а не возвращает весь проект к прежнему снимку.

При `revert` могут возникнуть конфликты, в том числе при отмене одного коммита. Разрешаются они уже знакомым способом: исправьте конфликтующие файлы, удалите маркеры и добавьте результат в индекс. Для нашего файла команды будут такими:

```bash
git add README.md
git revert --continue
```

Эти команды нужны только при остановке из-за конфликта. Чтобы отказаться от незавершённой отмены, используйте `git revert --abort`. Для отмены коммита слияния нужно дополнительно выбрать родителя через `-m`; в нашем примере отменяется обычный коммит.

Данный способ отката считается наиболее мягким, потому что сохраняет историю. Другим разработчикам не нужно перестраивать свои ветки из-за замены уже опубликованных коммитов. С `reset` ситуация отличается. [Документация `git revert`](https://git-scm.com/docs/git-revert).

### `reset` или как скрыть следы преступления

Для примера работы `reset` давайте сделаем отдельную ветку с названием `reset_example`. Создадим её от `revert_example`, чтобы не генерировать новые коммиты:

```bash
git switch revert_example
git switch -c reset_example
git log --oneline -4
```

```text
3c7cfbe (HEAD -> reset_example, revert_example) Revert "broken version"
00b4269 broken version
6517733 stable version
dce265e (main) Resolve weather conflict
```

Давайте переместим ветку на коммит `broken version` с помощью `reset`:

```bash
git reset HEAD~1
```

Здесь `HEAD~1` указывает на коммит, **на который нужно переместить указатель текущей ветки**. После выполнения команды Git скажет, что теперь `README.md` находится в изменённом состоянии:

```text
Unstaged changes after reset:
M       README.md
```

Это произошло потому, что по умолчанию `reset` работает в режиме `--mixed`. Этот режим перемещает текущую ветку на выбранный коммит и приводит индекс к нему, но сохраняет файлы рабочего дерева. Ветка теперь указывает на сломанную версию, а в файле всё ещё записано `App status: working`. Разница между файлом и индексом отображается как неподготовленное изменение:

```bash
git status
```

```text
On branch reset_example
Changes not staged for commit:
        modified:   README.md

no changes added to commit (use "git add" and/or "git commit -a")
```

И давайте убедимся, что положение ветки изменилось:

```bash
git log --oneline -3
```

```text
00b4269 (HEAD -> reset_example) broken version
6517733 stable version
dce265e (main) Resolve weather conflict
```

Коммит `Revert "broken version"` больше не входит в историю `reset_example`, но остаётся доступен через ветку `revert_example`.

Режим `--mixed` сбрасывает индекс. Если мы хотим оставить индекс без изменений, есть режим `--soft`. Для демонстрации сначала восстановим `reset_example` до вершины `revert_example`:

**Следующая команда с `--hard` перезаписывает индекс и отслеживаемые файлы. Она может уничтожить незакоммиченные правки, а также удалить неотслеживаемые файлы и каталоги, мешающие восстановлению отслеживаемых файлов.** В нашем учебном примере нужное содержимое сохранено в `revert_example`; свои дополнительные правки перед командой сохраните отдельно.

```bash
git reset --hard revert_example
git log --oneline -4
```

```text
3c7cfbe (HEAD -> reset_example, revert_example) Revert "broken version"
00b4269 broken version
6517733 stable version
dce265e (main) Resolve weather conflict
```

И опять выполним команду `reset`, но с флагом `--soft`:

```bash
git reset --soft HEAD~1
git status
```

```text
On branch reset_example
Changes to be committed:
        modified:   README.md
```

Видим, что ветка снова указывает на `broken version`, а индекс и рабочее дерево сохранились. Отличие индекса от выбранного коммита теперь подготовлено для нового коммита.

Если мы хотим привести к выбранному коммиту и ветку, и индекс, и отслеживаемые файлы, есть флаг `--hard`. Давайте вернём `reset_example` к коммиту, от которого начинали упражнение: на него по-прежнему указывает `main`.

**При следующей команде незакоммиченные правки будут отброшены**, включая подготовленное изменение из предыдущего шага:

```bash
git reset --hard main
git status
git log --oneline -1
```

```text
On branch reset_example
nothing to commit, working tree clean

dce265e (HEAD -> reset_example, main) Resolve weather conflict
```

Теперь индекс и отслеживаемые файлы соответствуют выбранному коммиту. Другие неотслеживаемые файлы, которые не мешают восстановлению, могут остаться на диске.

Такой откат меняет историю текущей ветки, что может создать проблемы для других разработчиков при синхронизации опубликованной истории. Такие изменения нужно обсуждать внутри команды, чтобы ни для кого это не стало сюрпризом. [Документация `git reset`](https://git-scm.com/docs/git-reset).

## `rebase`: переносим коммиты на другую основу

Помимо `merge`, у нас есть ещё одна команда, с помощью которой мы можем включать изменения другой ветки в свою линию разработки, — `rebase`. Чтобы продемонстрировать различия, давайте создадим ветку `feature_merge` от `main` и сделаем там пару коммитов. Начните с чистого рабочего дерева:

```bash
git switch main
git switch -c feature_merge
```

Добавьте в конец `README.md` строку `First feature`, сохраните файл и выполните:

```bash
git commit -a -m "first change"
```

Замените эту строку на `Second feature`, сохраните файл и создайте второй коммит:

```bash
git commit -a -m "second change"
```

Затем вернёмся в ветку `main` и сделаем в ней коммит, который меняет другой файл, чтобы в нашем примере не было конфликта при `merge`:

```bash
git switch main
```

Создайте в редакторе файл `additional.txt` с любой учебной строкой и сохраните его. Добавим файл в индекс и создадим коммит. Затем сохраним положение ветки в отдельной ветке `merge_base`, чтобы позже вернуться к нему без копирования хеша:

```bash
git add additional.txt
git commit -m "additional file"
git branch merge_base
git merge --no-edit feature_merge
git log --oneline --graph -4
```

```text
*   7ab12cd (HEAD -> main) Merge branch 'feature_merge'
|\
| * 5eeea85 (feature_merge) second change
| * 956d1e0 first change
* | 2b26938 (merge_base) additional file
```

Обратите внимание, что создан коммит слияния с двумя родителями. Оба исходных пути разработки сохранились. Теперь давайте сделаем `reset`, чтобы вернуть ветку к состоянию до `merge`, и применим `rebase`.

```bash
git reset --hard merge_base
git rebase feature_merge
git log --oneline --graph -3
```

```text
* 8368f0c (HEAD -> main) additional file
* 5eeea85 (feature_merge) second change
* 956d1e0 first change
```

В этом примере мы находились в `main`, поэтому Git взял изменения её коммита `additional file` и применил их поверх `feature_merge`. Для этих изменений создан новый коммит с новым родителем и другим хешем. Коммиты `first change` и `second change` остались прежними. Тем самым у нас получилась новая история ветки `main`.

Главное отличие в этом примере: `merge` сохраняет существующие коммиты и соединяет линии разработки коммитом слияния, а `rebase` создаёт новые версии переносимых коммитов поверх другой основы. Когда возможно слияние через fast-forward, `merge` при стандартных настройках просто перемещает ветку вперёд и отдельного коммита слияния не создаёт.

Rebase удобно использовать для актуализации собственной ветки. Например, у вас есть ветка `task1`, но пока вы что-то в ней делали, в `main` появились изменения. Если локальная `main` уже обновлена, в ветке задачи можно выполнить:

```bash
git switch task1
git rebase main
```

Git последовательно применит изменения коммитов задачи поверх актуальной `main`, создавая для переносимых изменений новые коммиты. Сама `main` при этом не перемещается.

При rebase могут возникнуть конфликты на нескольких переносимых коммитах. Исправьте конфликтующие файлы, добавьте результат через `git add` и выполните `git rebase --continue`. Для отказа от незавершённого переноса используйте `git rebase --abort`. [Документация `git rebase`](https://git-scm.com/docs/git-rebase).

## `cherry-pick` или как отобрать только нужные изменения

Предлагаю закончить разговор об основных командах Git черри-пикингом. Представим, что один из разработчиков делает в своей ветке какие-то новые фичи и удачно разбивает их на коммиты. Вам срочно нужна только одна из них. Для этого в Git есть команда `cherry-pick`: она применяет изменения выбранного коммита к текущей ветке и обычно создаёт новый коммит.

Давайте вернём `main` к состоянию до слияния из предыдущего примера и попробуем получить из `feature_merge` только изменения коммита с сообщением `second change`.

```bash
git switch main
git reset --hard merge_base
git log feature_merge --oneline -2
git cherry-pick feature_merge
```

В нашем примере ветка `feature_merge` указывает именно на коммит `second change`. Поэтому команда выбирает только этот коммит, а не всю историю ветки. Можно указать и его хеш из своего `git log`: например, `git cherry-pick 5eeea85`, если у вас выбранный коммит имеет такой идентификатор.

Здесь возникнет конфликт: выбранный коммит заменяет `First feature` на `Second feature`, а строка `First feature` была добавлена предыдущим коммитом, который мы не переносили. Разрешим конфликт знакомым способом. Откройте `README.md`, сохраните его прежнее содержимое и добавьте в конец строку `Second feature`, удалив маркеры конфликта. Затем выполните:

```bash
git add README.md
git cherry-pick --continue
git log --oneline -3
```

Если открылся редактор сообщения коммита, сохраните предложенное сообщение и закройте редактор. Для отказа от незавершённого переноса используйте `git cherry-pick --abort`. Если в другом примере конфликтов нет, команда создаст коммит сразу, и `--continue` не понадобится.

```text
998fddc (HEAD -> main) second change
2b26938 (merge_base) additional file
dce265e Resolve weather conflict
```

Видим, что изменения перенесены. Обратите внимание: мы взяли изменения выбранного коммита, а сам коммит создали новый. Исходная ветка `feature_merge` осталась на прежнем месте. [Документация `git cherry-pick`](https://git-scm.com/docs/git-cherry-pick).

## Локальные и удалённые репозитории

Пока наш репозиторий находится на компьютере. Как подключить других разработчиков? Можно передавать архивы, но удобнее иметь общий удалённый репозиторий и обмениваться с ним изменениями через Git.

На курсе мы будем пользоваться GitLab. Он доступен как облачный сервис и как система, которую организация может разместить на своих серверах.

Проверим, какие удалённые репозитории настроены:

```bash
git remote -v
```

Пока команда ничего не выведет. **Remote** — это именованная настройка подключения к другому репозиторию. Она обычно содержит адрес, откуда получать изменения и куда их отправлять. Само добавление remote ещё не синхронизирует репозитории.

Войдите в GitLab. Если сервер требует двухфакторную аутентификацию (2FA), настройте её по инструкции сервера и сохраните коды восстановления. При 2FA вход подтверждается дополнительным фактором, например кодом из приложения-аутентификатора.[Двухфакторная аутентификация](https://docs.gitlab.com/user/profile/account/two_factor_authentication/).

### Настраиваем SSH

Для обмена данными GitLab поддерживает SSH и HTTP(S). В связи с политикой информационной безопасности на нашем GitLab доступно взаимодействие только по SSH.

SSH позволяет подключаться с использованием пары ключей: публичный ключ добавляют в GitLab, а приватный остаётся на вашем компьютере. Сначала проверьте, нет ли у вас уже подходящего ключа в `~/.ssh`: не перезаписывайте существующие ключи.

Чтобы создать новую пару, выполните в Git Bash:

```bash
ssh-keygen -t ed25519
```

Команда предложит выбрать путь сохранения и парольную фразу. Если путь по умолчанию свободен, можно принять его. Парольная фраза защищает приватный ключ на диске; её рекомендуется задать. Если программа спрашивает, нужно ли перезаписать существующий файл, не соглашайтесь без понимания, где используется старый ключ. При выборе другого имени файла SSH может потребоваться настройка для использования этого ключа.

При стандартном пути приватный ключ будет в `~/.ssh/id_ed25519`, а публичный — в `~/.ssh/id_ed25519.pub`. Выведите **публичный** ключ:

```bash
cat ~/.ssh/id_ed25519.pub
```

Скопируйте всю строку. Приватный ключ из файла без `.pub` нельзя передавать другим людям или загружать в репозиторий.

Откройте меню профиля и настройки:

![Переход к настройкам профиля GitLab](files/Pasted%20image%2020260930181507.png)

В интерфейсе на снимке путь такой: `Access → SSH keys → Add new key`.

![Раздел SSH keys](files/Pasted%20image%2020260930181543.png)

Вставьте публичный ключ, укажите понятное название, при необходимости срок действия и нажмите `Add key`:

![Добавление публичного SSH-ключа](files/Pasted%20image%2020260930181700.png)

При первом SSH-подключении может появиться запрос о доверии ключу сервера. Сверьте его отпечаток с данными администратора учебного GitLab, прежде чем подтверждать. Это ключ **сервера**, а не ваш пользовательский ключ. [SSH-ключи в GitLab](https://docs.gitlab.com/user/ssh/).

### Создаём проект и отправляем историю

Откройте `Projects → Create a project`:

![Создание проекта GitLab](files/Pasted%20image%2020260930174823.png)

Выберите `Create blank project`, задайте имя `ai-agent` и доступность проекта. Я использую приватный проект.

Так как локальная история у нас уже есть, **не включайте `Initialize repository with a README`**. Не нужно создавать на сервере отдельный начальный коммит.

![Настройки нового проекта](files/Pasted%20image%2020260930175042.png)

GitLab покажет инструкции для отправки существующего репозитория.

Скопируйте SSH-адрес созданного проекта. В следующем примере адрес вымышленный — **замените его точным адресом из GitLab**, включая порт, если он указан:

```bash
git remote add origin git@gitlab.example.org:student/ai-agent.git
git remote -v
git push --set-upstream origin main
```

Первая команда добавляет remote с именем `origin`. Это общепринятое имя, но можно выбрать другое. Один локальный репозиторий может иметь несколько remote.

`git push` отправляет необходимые объекты и обновляет указанную ветку на сервере. Команда не отправляет незакоммиченные файлы рабочего дерева. `--set-upstream` связывает локальную `main` с `origin/main` как с upstream-веткой, то есть веткой, используемой для обмена изменениями при соответствующих настройках команд.

Вместо одной ветки можно отправить все локальные ветки:

```bash
git push --set-upstream origin --all
```

[Отправка изменений](https://git-scm.com/docs/git-push).

Обновите страницу проекта. В ней появятся отправленные файлы и история.

![Файлы проекта после отправки истории](files/Pasted%20image%2020260930183048.png)

В Markdown `# Заголовок` задаёт заголовок первого уровня, `**текст**` — полужирное выделение, `*текст*` — курсив. [Синтаксис Markdown в GitLab](https://docs.gitlab.com/user/markdown/).

## `clone`, `fetch`, `pull`, `push`

Репозиторий можно создать и в обратном порядке: сначала в GitLab, затем получить локальную копию. Для отдельного упражнения создайте второй проект, например `ai-agent2`, и на этот раз включите `Initialize repository with a README`.

![Проект, инициализированный с README](files/Pasted%20image%2020260930183833.png)

GitLab создаст начальный коммит. [Создание проекта GitLab](https://docs.gitlab.com/user/project/).

Откройте `Code` и скопируйте адрес `Clone with SSH`:

![Копирование SSH-адреса репозитория](files/Pasted%20image%2020260930184047.png)

Перейдите в родительский каталог, чтобы не создавать один репозиторий внутри другого. Замените вымышленный адрес ниже адресом своего проекта:

```bash
cd ..
git clone git@gitlab.example.org:student/ai-agent2.git
cd ai-agent2
git log --oneline
```

При обычном клонировании Git создаёт каталог проекта, получает историю, настраивает `origin` и создаёт рабочее дерево для выбранной начальной ветки. Как правило, локально сразу создаётся только эта ветка, а для остальных полученных веток остаются ссылки вида `origin/имя`. [Клонирование репозитория](https://git-scm.com/docs/git-clone).

Пример истории:

```text
ec4fdb0 (HEAD -> main, origin/main, origin/HEAD) Initial commit
```

`main` — локальная ветка. `origin/main` — локальная ссылка, отражающая известное Git состояние ветки на сервере; она не обновляется сама по себе при чужом коммите. `origin/HEAD` обычно указывает на известную основную ветку remote.

Основные команды обмена:

| Команда | Что делает |
| --- | --- |
| `git clone` | Создаёт локальную копию репозитория. |
| `git fetch origin` | Получает объекты и обновляет ссылки вроде `origin/main`; при обычном использовании не изменяет текущую локальную ветку и рабочие файлы. |
| `git pull` | Получает изменения и интегрирует их в текущую ветку. Способ интеграции зависит от опций и настроек: например, слияние или rebase — перенос локальных коммитов поверх другой основы. |
| `git push` | Отправляет необходимые объекты и предлагает обновить ветки или другие указанные ссылки на сервере. |

## Merge request

Продолжим во втором проекте `ai-agent2`. Создадим ветку для первой задачи:

```bash
git switch main
git switch -c task1
```

Измените `README.md` в редакторе и сохраните. Например:

```markdown
# Репозиторий проекта по дисциплине «Информационные технологии»

Здесь будет учебный ИИ-агент для управления задачами.
```

Подготовьте изменение, проверьте его, создайте коммит и отправьте ветку:

```bash
git add README.md
git diff --staged
git commit -m "Update project description"
git push --set-upstream origin task1
```

Теперь `task1` опубликована в удалённом репозитории. GitLab может вывести в терминале ссылку на создание MR и показать кнопку `Create merge request` на странице проекта:

![Предложение создать merge request](files/Pasted%20image%2020260930185055.png)

**Merge request** — запрос на включение изменений из одной ветки в другую. Это функция GitLab, а не отдельная команда Git. В командной работе часто используют такой порядок: разработчик делает изменения в своей ветке, открывает MR, другой участник проводит **ревью**, то есть проверяет изменения и оставляет замечания. После проверки изменения сливают в основную ветку.

Для нашего задания выберите исходную ветку `task1` и целевую `main`. Напишите понятное название и описание: что сделано и как вы проверили результат. Укажите меня как reviewer — участника, которому поручена проверка.

Сначала нужно дать мне доступ к проекту. В интерфейсе на снимках для этого используется `Manage → Members → Invite members`. Введите мой логин, и назначьте роль `Developer`.  [Участники проекта](https://docs.gitlab.com/user/project/members/).

`Approve` означает одобрение MR, а `Merge` запускает слияние.  [Одобрения MR](https://docs.gitlab.com/user/project/merge_requests/approvals/), [защищённые ветки](https://docs.gitlab.com/user/project/repository/branches/protected/).

По правилам курса **сливать MR или PR до одобрения преподавателя нельзя**, даже если интерфейс технически разрешает это. После одобрения слияние выполняет участник с нужными правами, когда выполнены остальные требования проекта и устранены конфликты.

## Работа с GitHub

GitHub можно использовать и для личных проектов, и для выполнения лабораторных работ курса. Лекции и задания будут дублироваться там; для сдачи работы создавайте PR и предоставляйте преподавателю доступ к репозиторию. Команды Git остаются теми же: `clone`, `fetch`, `pull`, `push`, ветки и коммиты работают независимо от выбранной платформы.

### Создаём репозиторий и подключаемся

Создайте аккаунт GitHub и выберите создание репозитория — `New repository`. Задайте имя и видимость: `Public` для открытого проекта или `Private` для приватного. Если вы собираетесь отправить уже существующую локальную историю, не добавляйте при создании README, лицензию и `.gitignore`: эти файлы можно подготовить локально. [Создание репозитория GitHub](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository).

GitHub поддерживает SSH и HTTPS. Для SSH можно использовать уже созданную пару ключей или отдельную пару. Добавьте **публичный** ключ в `Settings → SSH and GPG keys → New SSH key` своего аккаунта. Приватный ключ остаётся на компьютере; при необходимости настройте SSH на его использование. При первом подключении проверьте отпечаток ключа сервера. [Добавление SSH-ключа](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account).

В новом локальном репозитории без настроенного remote команды выглядят так. Замените `YOUR_USERNAME` своим именем пользователя, а `ai-agent` — именем созданного проекта:

```bash
git remote add origin git@github.com:YOUR_USERNAME/ai-agent.git
git push --set-upstream origin main
```

Если `origin` уже ведёт в GitLab, не нужно добавлять его повторно. Можно сохранить оба подключения, назвав второе `github`:

```bash
git remote add github git@github.com:YOUR_USERNAME/ai-agent.git
git push github main
git remote -v
```

Здесь мы намеренно не меняем upstream основной ветки: работа с учебным GitLab продолжается через `origin`. Отправка в GitLab не обновляет GitHub автоматически, и наоборот.

Для получения готового проекта скопируйте SSH-адрес через кнопку `Code` и выполните `git clone` из родительского каталога проектов:

```bash
git clone git@github.com:YOUR_USERNAME/ai-agent.git
```

### Pull request вместо merge request

В GitHub запрос на слияние называется **pull request (PR)**. Он похож на MR в GitLab.

Рабочий порядок тот же: создайте ветку, измените файлы, создайте коммиты и отправьте ветку. Если GitHub подключён как `origin`:

```bash
git switch main
git switch -c github_task1
```

Отредактируйте и сохраните `README.md`, затем выполните:

```bash
git add README.md
git commit -m "Update project description"
git push --set-upstream origin github_task1
```

Если подключение называется `github`, используйте вместо последней команды `git push github github_task1`.

На странице проекта откройте `Pull requests → New pull request` или предложенную кнопку `Compare & pull request`. В поле **base** выберите целевую `main`, а в **compare** — ветку `github_task1`. Заполните название и описание, создайте PR и назначьте reviewer. [Создание pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request).

Для совместной работы в своём репозитории пригласите участника через настройки доступа. При отсутствии прав на запись в чужой проект часто используют **fork** — отдельную копию репозитория на GitHub под своим аккаунтом — и предлагают изменения через PR из неё. Возможность создать fork зависит от видимости репозитория и настроек доступа. [Управление доступом](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-teams-and-people-with-access-to-your-repository).

## Как будет выглядеть работа весь семестр

Для каждой лабораторной работы создавайте отдельную ветку: `task1`, `task2`, …, `task6`. Выполняйте задание в ней, создавайте MR в GitLab или PR в GitHub с целевой веткой `main` и ждите проверки преподавателя.

Обычный порядок работы:

1. После слияния предыдущей работы переключитесь на `main` и получите её актуальное состояние через `git pull`.
2. Создайте новую ветку для следующего задания.
3. Вносите изменения и фиксируйте их осмысленными коммитами.
4. Отправьте ветку на выбранную платформу и создайте MR или PR в `main`.
5. Исправляйте замечания в той же ветке и отправляйте новые коммиты: они появятся в уже открытом MR или PR.
6. После одобрения и выполнения требований проекта завершите слияние и защитите работу очно.

В конечном итоге в `main` будет собираться полноценное приложение.
